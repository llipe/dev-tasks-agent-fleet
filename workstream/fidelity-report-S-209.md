## 1. Human-readable summary

This story builds the one message the code-review agent sends to the model. It does three things.

First, it keeps the message within the size allowance. The instructions and the code changes always go in. If those two alone are too big, the review is refused with a "too big to review" result, as the PRD requires. Everything else is added in a fixed priority order until the allowance runs out: the pull request description, the verifier's critical drift items, the linked issues, the verifier's drift section, the spec, the repository's house rules, and finally whole files, smallest first. Anything cut short or left out is recorded, so the comment can say so later. Critical drift items that do not fit are not lost. They are recorded and will count against the pull request, so a large pull request cannot hide verifier drift. The final size is checked before anything is sent, and an oversize message is treated as a bug.

Second, it writes the reviewer's rules: the rubric (version 1) and the system instructions. They state the four kinds of finding, the rule that every finding must say what goes wrong, what is out of scope (the verifier's job, CI's job, security scanning), and that the pull request description is the author's claim, not the truth. They also tell the model how to check each critical drift item.

Third, it fences off everything the author controls. Each piece of pull request, issue, spec, report, or file text sits between marker lines that carry a random code chosen per run. The builder checks that this code appears nowhere inside the content, so text in a pull request cannot close a fence or pose as an instruction.

Everything the story asked for is present and tested, and the independent re-run passes. The deviations from the written plan are deliberate and recorded in the pull request. They include how the wrapper text is counted, how shared limits are split, how cuts are named, and a stronger check on the random code. Each should be written back into the spec or test plan.

Four questions remain open, none of them a defect in this story. (1) One phrase in the rubric's "intent" category could invite the model to report missing requirements, which is the verifier's job. (2) The size estimate is too low for Chinese, Japanese, or Korean text and for emoji, and the planned retry does not help when the code changes themselves are the large part. (3) The model's reply and the "repair" request are not counted in the size allowance. The next story (S-210) owns that. (4) The PRD asks for the verifier report's verdict line, and the spec does not. That question is already with the user.

**Story business rules.** _The PR description is the author's claim_ (FR-12): the PR block's label says "(the author's claim)", and the system prompt says it outright. _Fidelity is the verifier's job_ (FR-14): the rubric's boundary section says so in the PRD's words. **Judgment 1: does the wording encode the requirements?** Yes, with one caveat. The rubric and system prompt match FR-12, FR-13, FR-15, FR-20, FR-21, and D-33 closely, often word for word. FR-21's list is verbatim. FR-20's sub-items are all present. D-33's two statuses and their two `not_reproduced` grounds are exact, and the §8.7 default ("a candidate you leave out is counted as confirmed") is stated. FR-13's "no authority" rule covers forged markers and requests to report nothing. FR-14 is stated in the boundary section, but the `intent` category definition ("the code does not do what … the linked issues or the spec say it is meant to do") reads like an AC-coverage check (DR-10). Whether the model obeys any of this is a model behavior. It can be shown only live (test plan G-3, SC-LIVE-04, SC-LIVE-11, S-215).

**Judgment 2: is the budget invariant the spec's invariant?** Yes. Spec §8.4 defines `I` as "instructions + rubric + schema" and asserts `estimate(prompt) ≤ B`. The delivered `I` is the fallback system prompt, which is exactly instructions, rubric, and schema, plus the preamble and a 250-token notes reserve. The final check runs on the real strings. Counting the fallback form covers both call shapes. On the forced path, the adapter sends `system` (1,536 tokens) and the schema in `toolConfig` (302 tokens compact, 613 as indented JSON). That is at most 2,149 tokens against the 2,180 the fallback form charges (auditor probe), so the forced path is slightly over-counted, which is the safe direction. Two things are not counted: the provider's own wrapping of the tool definition, which cannot be known without a tokenizer and is small, and anything outside the first call (DR-12). The delivered `I` is about 2,500 tokens, against the spec's "~6k" (DR-1). The invariant holds only if S-210 sends the strings `Prompt` returns, which is why pinned decision 2 must become an S-210 rule.
