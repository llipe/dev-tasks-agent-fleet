## 1. Human-readable summary

This story adds the step that checks the AI reviewer's findings before anyone sees them, and decides whether the review says "blocking" or "clear".

The model's answer is not trusted. A finding is marked blocking only when it points at code the pull request changed and explains how the code fails. Otherwise it is shown as a suggestion. A finding about a file the pull request did not change, or a finding that does not say what breaks, is removed. Only the top-ranked suggestions are kept, up to the configured number. Blocking findings are never cut. Every downgrade and removal is counted for the run's metrics, and no finding text goes into those counts.

The verdict is computed here too. It is "blocking" when at least one blocking finding remains, or when the verifier reported a serious, unintended drift that the model did not show to be stale. When the model skips one of those drift items, it still counts. When a drift item was left out of the prompt because of the size limit, it always counts, because the model never saw it. This matches the user's decisions D-15, D-33, and D-37.

Three rules were tightened after the quality pass, and the planner accepted them. A blocking finding may cover at most 200 lines (D-50). A scenario or consequence counts as blank when it has no letter or digit, so "." or "—" is blank, while "N/A" is not (D-51). File names that contain a backslash are now shown in an unambiguous form.

What should be written down next: the spec and the test plan do not yet carry these rules, and D-50 and D-51 are not yet in the decision log. One open question deserves a product decision (DR-2). The model is not told about the 200-line limit, the limit applies even when every line in the span is changed code, and such a finding is labelled "outside the diff". In that case a real problem in a large new function can become a suggestion, and if five better-ranked suggestions exist, it is not shown at all.

**Story business rules.** _No scenario, no block_ (PRD §8): no output blocking finding has a blank scenario; RT-08 asserts it on every iteration. _The model can filter stale drift out, never ignore it_ (spec §8.7): an omitted candidate counts; a dropped candidate counts whatever the model says; a `not_reproduced` for an unknown or dropped ID clears nothing. Technical notes: `file` normalization (backticks, `./`, leading `/`) and the swap are delivered as written.

**Judgment 1: do the rules and the verdict match §8.6/§8.7, D-08, D-33, and D-37?** Yes. The order is §8.6's (schema re-check, location, scenario, consequence, cap, IDs), and the first rule that applies decides, so a finding outside the diff with no scenario is `outside_diff`, as TC-211-06 requires. D-08 is literal: the wrapper downgrades and drops; nothing the model says about severity survives unchecked. The verdict is `blocking` iff a blocking finding or a counted candidate remains. D-33 is literal: only `not_reproduced` stops a shown candidate from counting, and only for a candidate the model was shown. D-37 and §8.4 step 5 hold in the strongest form: a candidate dropped for budget is `dropped_for_budget` and counted even when the model returned a check for its ID (auditor probe: `V2` dropped, `not_reproduced` from the model, still counted, check counted as ignored). If an ID were both shown and dropped, the dropped side still counts (QA test). The duplicate rule (any `confirmed` wins) leans toward blocking, which is D-15's default. The only differences are in vocabulary: the spec says an omitted candidate is "treated as `confirmed`", and the code gives it its own `not_checked` status with `counted=True` (DR-7).

**Judgment 2: is D-50 consistent with "a blocking finding exists only when it points at changed code"? Could it downgrade legitimate findings badly?** It is consistent with PRD §8 ("Blocking requires a location in the diff") and with the story's wording. It is stricter than FR-23's literal text, under which a span that touches a hunk does not "fall outside" it. A span of `1` to `10**300`, or a whole file around one changed line, names no location, so bounding it is right, and the error direction (toward suggestion) matches the PRD's noise goal. It can, however, downgrade a legitimate finding in one narrow case. The bound applies even when every line in the span is changed code. Auditor probe: a new 250-line function `new.py:1-250`, all of it added, with a concrete scenario and consequence, becomes `S1`, `outside_diff`, verdict `clear`. With five suggestions ranked at or above it, the cap drops it and it does not appear in the comment at all. Three factors make this more likely than it needs to be. The prompt's blocking contract does not mention the bound. The `outside_diff` label (artifact and metrics) cannot tell "too broad" from "elsewhere", so precision measurement (goal 4) cannot see the effect. And no rule exempts a span that lies inside the widened changed ranges. The risk is bounded: the prompt already asks for lines "the diff adds or changes", models normally anchor a blocking finding to a few lines, and a human still approves every merge. Classified **Minor, Undetermined** (DR-2). Recommended: one sentence in the prompt's blocking contract (rubric v1 is unshipped), and a product decision on the exemption and on a distinct counter.

**Judgment 3: does D-51 match "no scenario, no block"?** Yes for the letter, and it is stronger than the test plan. FR-23 says "empty", TC-211-06 lists whitespace forms, and D-51 also treats punctuation, symbols, marks, format and zero-width characters, and the Hangul fillers as blank. So `"."`, `"-"`, `"—"`, `"…"`, `"?"`, `"​"`, and `"ㅤ"` downgrade a blocking finding (auditor probe). It does not enforce the rule's meaning against placeholder words: `"N/A"`, `"none"`, and `"TBD"` keep a blocking finding blocking. That residual is deliberate (no deny-list). A deny-list would be English-only, easy to evade (`"n/a."`, `"not applicable"`), and would misfire on real text. Judging whether a scenario is concrete is the model's job under the prompt's contract ("concrete inputs or a sequence of events"), and precision measurement observes it. A digit-only string such as `"42"` counts as non-blank; that is harmless. Classified **Minor, Intended** (DR-3).

**Judgment 4: is the `escape_path` change safe for S-206 and S-209 consumers?** Yes. Every consumer outside `validate` was checked. S-206 diff headers (`_header_path`) and S-209 prompt lines (the `path:` line of full files, the name-only list, report, candidate, and spec labels) call `escape_path`. The only new behavior is that `\` becomes `\\`. A path with `\` never reaches a diff header or a full-file block: the GitHub client's `_encode_path` + `_safe_encoded_segment` guard refuses it, and `diff.py` turns that into a name-only file (`content_unavailable`, `UNAVAILABLE_UNSAFE_PATH`), as `test_backslash_filename_is_content_unavailable_not_a_run_failure` and `test_backslash_previous_filename_is_content_unavailable` pin. Report and spec paths come from fixed `workstream/…` patterns with no `\`, and candidate labels are path plus row index. So in production the visible change is limited to the name-only list, where `a\b.py` now shows as `a\\b.py`. The prompt's token estimate is taken over the built text, so the extra character is counted. `changed_ranges` keys and `DiffContext` data stay raw. Injectivity is pinned over a hostile 11-symbol pool of names up to length 4. No S-206 or S-209 expectation changed in the diff; only tests were added. Classified with the path rules, **Minor, Intended** (DR-5).
