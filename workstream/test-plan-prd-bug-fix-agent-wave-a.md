# Compliance Test Plan — Bug Fix Agent, Wave A (verifier, Design Mode)

> Pre-implementation compliance test plan for **Wave A only** (stories S-180–S-189, GitHub issues
> #326–#335 in `llipe/dev-tasks-agent-fleet`), derived from
> [`prd-bug-fix-agent`](../docs/requirements/prd-bug-fix-agent.md) v1.2 (FR-1–FR-32, AC-1–AC-20),
> [`specification-prd-bug-fix-agent`](specification-prd-bug-fix-agent.md) v1.2,
> [`user-stories-prd-bug-fix-agent`](user-stories-prd-bug-fix-agent.md) v1.1 (S-180…S-189),
> [`tasks-prd-bug-fix-agent-plan`](tasks-prd-bug-fix-agent-plan.md) v1.0 (tasks 1.0–10.0), and
> [`decisions-bug-fix-agent`](decisions-bug-fix-agent.md) (D-01–D-43; D-40–D-43 supersede every Bedrock
> reference). Companion: [`traceability-matrix-prd-bug-fix-agent-wave-a`](traceability-matrix-prd-bug-fix-agent-wave-a.md).
>
> **Verdict context.** This is a Design Mode artifact, not an audit. It is additive and non-blocking and
> does not replace `make validate` (lint, format-check, typecheck, test, audit). Every numbered acceptance
> criterion maps to at least one positive and at least one negative or edge test.
>
> **`audit` caveat.** `audit` is currently red on `main` for an unrelated reason being fixed in parallel.
> No test in this plan requires `audit` (root or package `pip-audit`) to be green. Where a story AC names
> the audit step (S-180 AC5), the test checks that the step **is wired**, not that it passes.

### Layer and status vocabulary used below

| Code     | Meaning                                                                                                                     |
| -------- | --------------------------------------------------------------------------------------------------------------------------- |
| **L1**   | Unit: pure functions and static file contracts. No network, DB, or real clock.                                             |
| **L2**   | Component: entrypoint or module driven end to end with GitHub (`tests/fakes/fake_github.py`), PostgREST, Secrets Manager, `subprocess`, and the clock faked. |
| **L2.5** | Integration: real local Supabase (`panel/tests/integration/`, `probeLocalDb`).                                              |
| **IMG**  | CI image smoke (Docker buildx, linux/arm64). Skipped locally without Docker.                                                |
| **LIVE** | Manual or operator verification on the deployed runtime, evidenced in the change record or runbook. Not automated E2E.     |
| **R**    | Runnable now: needs only the code under test (local or CI).                                                                 |
| **R-DB** | Runnable now with the local Supabase stack.                                                                                 |
| **R-CI** | Runnable now on a CI runner with Docker/arm64.                                                                              |
| **OP**   | Blocked on S-188 operator prerequisites or deploy (App Issues r/w, `OPERATOR_GITHUB_LOGIN`, dedicated key, runtime ARN). Not canary-dependent. |
| **CAN**  | Blocked on the S-189 canary: either it *is* the canary observation, or its expected value depends on unverified CLI or platform behavior (D-28 **U** items, spec §17). |

## 7. Randomized and property-based tactics

**Adoption note.** The siblings declined `hypothesis` (see `test-plan-prd-security-analyst-agent.md` §6 and v1.1). These tactics use the standard library (`random.Random(seed)`), so they add no dependency to the `pip-audit` surface. The `developer` or `qa-engineer` makes the build-vs-skip call per tactic and records it in this file's changelog.

**Seed policy.** Seed string `<tactic>-<AC>-<unix-ts>-<hex4>`; the integer seed is `int(sha256(seed_str)[:16], 16)`. Each test reads `BUGFIX_RT_SEED` (default: the fixed seed below) and `BUGFIX_RT_ITERATIONS`. On failure it prints the seed, the iteration index, the minimized input, Python version, platform, and package version.
**Replay:** `cd agents/bug-fix/app/bugFix && BUGFIX_RT_SEED=<seed> BUGFIX_RT_ITERATIONS=1 python -m pytest tests/unit/<file> -k <RT id>`.
**Oracle rule.** Generators construct inputs from known parts, so the expected value comes from the generator, not from a re-implementation of the code under test (`TESTING.md`: "a test double must not reimplement the logic it stands in for").
