## 1. Human-readable summary

This story connects the parts built in S-204 to S-212 into one working review. When someone asks for a review, the agent:

1. loads the pull request;
2. gathers the changes and the context around them;
3. asks the model for a review;
4. checks the answer;
5. posts one comment.

Each run is recorded in the panel with its steps, its result, a stored copy of the review, and its costs and counts.

The story's promise is that "a review request never goes silent". In practice, the pull request gets one of these:

- a review;
- a note that it is too big to review;
- a new note that there is nothing to review, because only lockfiles or similar files changed;
- a short "Code review failed" note with a link to the run.

The agent posts nothing only in a few cases, each one deliberate:

- The request itself was invalid.
- The pull request is closed, merged, or does not exist.
- The agent could not get its GitHub access, so it has no way to post.
- GitHub refused the agent's comment outright.
- The machine was shutting down, or the caller hung up.
- Less than two seconds were left on the clock.

Every one of these cases is still recorded in the panel as a run with its reason.

Reviews have a time limit. The agent stops waiting one minute before the end, which leaves time for the failure note. Secrets are removed from everything the agent writes.

Most of the developer's choices only need to be written into the spec and the test plan. Two points need a product decision:

- If GitHub accepts the review but its reply is lost on the way back, the agent cannot tell that the review was posted. It then posts a failure note as well, so the pull request shows a review and a "failed" note side by side (DR-5).
- The new "nothing to review" note does not show the rubric version, and neither do the budget and failure notes. The PRD asks for the version "on every comment" (DR-9, the same question as S-212 DR-8).

With this story, every part of the base agent is built and tested on recorded data. Before anyone can use it, the agent must be deployed (S-214) and tested against real pull requests (S-215).

**Judgment 3: deadline and heartbeat per D-32 and §8.9.** Conformant.

- The deadline is `start + run_timeout_seconds − 60` on `time.monotonic` (`test_deadline_is_start_plus_timeout_minus_reserve`).
- It is checked before each step and after each worker phase. `bounded` raises `RunTimeout` at the deadline in real time and abandons the worker (`test_a_stuck_phase_is_abandoned_at_the_deadline`).
- A Converse call that returns after the deadline is `RUN_TIMEOUT`, with its tokens recorded (pinned 11).
- The Converse timeouts come from S-210's `call_timeouts(remaining)`. This is stricter than §8.9's `min(600, remaining)`, because the remaining time is split over botocore's three attempts. It is already recorded as S-210 DR drift, and the test asserts `≤ min(600, remaining)`.
- The heartbeat is the sibling `run_with_heartbeat` at `HEARTBEAT_INTERVAL` = 120. It wraps `load_pr` (token plus `GET pull`), `context` (all GitHub reads), and `review` (Converse), never `validate` or `post` (TC-213-18). Its chunks reach the entrypoint stream.
- `assert_clock_invariant()` runs at startup.
- The post phase sits inside the 60 s reserve. The review or note POST gets `post_timeouts(time_left/2)`, the failure comment gets `post_timeouts(time_left)` (connect ≤ 5 s, read ≤ 30 s), and under 2 s the failure comment is skipped.
- `validate` and `post` are not run under `bounded`. `validate` is pure CPU, and `post` is bounded by its timeouts. "Bounds each step" therefore means "checked before each step, and real-time-bounded for the three blocking phases". This is Minor, Intended (DR-6).
- Known limit: an abandoned worker keeps doing its remaining GitHub reads until they finish. Its results and events are discarded.

**Judgment 5: secrets per §12.** Conformant.

- **Registration.** The Supabase key is registered before the reporter exists, and the token before the first GitHub client.
- **run_events.** Every event goes through `_Events`, which runs `scrub` over the message and every nested data value. Events carry fixed messages and counts only. They never carry prompt, model, or repository text, and never a reviewed path.
- **Step failures.** A failed step records `CODE (Class)` with no traceback.
- **`runs.error_message`.** It is built from the code, the step, the class, and the HTTP status. Exception text is added only for the wrapper's own `BedrockAdapterError`, `RunTimeout`, and `CommentPostFailed`.
- **Exceptions reaching `main.invoke`.** `_ScrubbedRunReporter` and the `except` in `main.invoke` record the class name only.
- **Comment bodies.** `_scrub_validation` and `_scrub_render_inputs` scrub model and repository text before rendering and before the renderer's cuts (QA-213-06). `_scrub_body` then removes each secret in its raw, `neutralize`d, and `code_span` forms.
- **Artifact metadata.** `scrub_value` runs over the whole metadata tree.
