## 1. Human-readable summary

This story teaches the code-review agent what a pull request was meant to do. It finds the issues the pull request says it closes, either from phrases such as "Closes #315" in the description or from a branch named `issue/315-…`. It reads up to five of them. It ignores links to other repositories and skips links that turn out to be pull requests.

Each issue is passed with its title, labels, and description, but the developer's own plan at the bottom ("Task Checklist") is cut off. The PRD says the reviewer must not see the author's plan, so that it judges the work independently. Each issue is also limited in size.

The agent then finds the specification each issue belongs to: a specification file named in the issue, else the PRD name in the issue title, else a PRD label. If the specification is too large for its share of the review, the agent keeps its table of contents, the sections the issue cites (for example "Spec §8.1"), and the sections that mention the story or the files being reviewed. If the agent is not allowed to read an issue, it skips that issue and records the gap instead of failing the review.

Everything the story asked for is present and tested, and the independent re-run passes. The team made several decisions along the way that the spec does not yet record. The main ones: a link that turns out to be a pull request still uses one of the five slots; when several specifications are found, they share one size allowance; and the "Task Checklist" heading is recognised in every form GitHub displays as a heading, not only the exact form the spec gives. Testing also found four weaknesses against deliberately hostile input, such as very long runs of spaces and unusual line endings. All four are fixed. None of the differences changes what the reviewer is shown in a harmful way. Each should be written back into the spec.
