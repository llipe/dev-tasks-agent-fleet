## 1. What changed and why (plain language)

The bug-fix agent will let an AI model edit code and run a target repository's own scripts inside a container that also holds real credentials. This story had to prove, on the real hosting platform rather than a laptop, that the model and those scripts are walled off from the credentials and the internet. Package registries are the one allowed exception.

The first attempt on the real platform failed. The platform forbids the privilege-switching tool (`sudo`) that the design used to move from the credential-holding process to the restricted user. The team changed the design (decision D-110): the main process now starts with full privileges and permanently drops them for every restricted process. A second problem followed. The sandbox needs the name `localhost` to work, and the platform supplies an empty, locked hosts file. The team fixed that in the container image itself (decision D-111). On the fourth run, every one of the 39 checks passed. The test switch (`ALLOW_PROBE`) was then removed, and the platform now refuses test runs.

What's still not fully proven: the checks showed that the AI tool's own rules block forbidden commands such as `git push` and web fetches. They didn't directly show that an ordinary allowed shell command from the AI runs inside the network wall. The repository-script path was shown directly. The spike report flags this, but no task or issue tracks it yet. The written technical specification also still describes the old design (a separate non-root "wrapper" user and `sudo`-era assumptions), so later stories would read an outdated contract.

### Questions the caller asked

- **Delivered design vs spec/PRD intent.** The PRD is uid-agnostic ("runs as a separate user", FR-9), so the root wrapper + `setpriv`, `srt` for scripts, the CLI's own sandbox, and image NSS all match PRD intent. All four are recorded decisions (D-110, D-111) accepted by @llipe. The spec is behind: it has no `sudo` text, but it still describes a `wrapper` uid and directory ownership that no longer exist (DF-182-01) and a single sandbox runtime (DF-182-02). A spec changelog entry (v2.2) is needed.
- **Open question 3 and AC3–AC5.** It doesn't change the AC3–AC5 verdicts as worded. AC3/AC4 are satisfied on the script path. AC4's uid-level checks (`proc.wrapper.uid`, `env.fixer.uid`) also cover the CLI process, which runs as the same `setpriv`-dropped `fixer`. AC5 is a permission-layer property. It does matter for the **story intent** and for **S-191**. S-191 is the first story that lets the model run allowed Bash (`node -e`, `python3 -c`, test runners) with network. If the CLI's Bash sandbox didn't apply there, the only network barrier on the model path would be untested. The uid drop and env stripping still hold, so the container-credential endpoint lacks its auth token, but IMDS reachability on the model path is unmeasured. It should be closed **before Wave B runs the CLI on a real issue**, ideally as an IC task in S-191 or S-195 (SC-IC-07 is a natural host).
- **Runbook coverage.** Not a finding. The PR has well over three setup/infra steps (redeploys, the `ALLOW_PROBE` toggle, image changes), and it **updates** `docs/runbooks/bug-fix-agent.md` (trigger, root-wrapper and NSS facts, "Run the sandbox probe" procedure, result-reading guide) and the index trigger. Only the index's "last verified" label is stale (DF-182-08).
