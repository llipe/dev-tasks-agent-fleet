## 1. Human-readable summary

This story sets up the code-review agent's base: an empty agent that starts, checks its input, and reports back, which the later stories fill in. The panel now has a "Code Review" agent with six settings: the pull request number, which is required, and five limits with sensible defaults. The agent checks those settings itself as a second line of defense. If anything is wrong, it records a clear "invalid parameters" failure and never contacts GitHub. When the input is valid, it starts the run, begins its first step, and stops with a "not implemented" message. That is the expected behavior until story S-213 adds the real review. The agent's automated checks now run in CI alongside the other two agents.

Everything the story asked for is present and tested, and the tests pass when run independently. Two items still need an environment with Docker: loading the new agent into a local database, and looking at its form in the panel. A small part of one check waits for the deployment story (S-214). A few deliberate departures from the "copy the sibling agent" approach make the agent more correct, not less. Two open questions go to product-engineer. One: whether the new agent should be switched on before it is deployed (it now appears first in the panel's agent lists). Two: whether a pull request number written as `7.0` should be accepted.
