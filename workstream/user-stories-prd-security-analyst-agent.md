### Story S-125: Project scaffolding, reporting, and credential reuse (deployable no-op)

**Priority:** Critical
**Estimated Size:** M
**Dependencies:** None — first story.

#### User Story

As an operator, I want the `security-analyst` AgentCore project scaffolded, deployable, and reporting a real run to Supabase using the fleet's existing credentials, so every later story lands on a proven pipe instead of debugging deployment and auth alongside scanner logic.

#### Context

Mirrors the sibling agent's own bring-up order: prove `agentcore create` → `agentcore deploy` → a `RunReporter`-wrapped run reaching Supabase, before any scanner is integrated. This story's entrypoint validates the payload and immediately reports `succeeded`/`no_findings` with zero scanners run — a deliberate placeholder outcome, not a shortcut.

#### Acceptance Criteria

- [ ] `/agents/security-analyst/` exists, generated by `agentcore create` (PRD AC1); `agentcore validate` passes.
- [ ] `agentcore deploy` provisions the runtime in `us-east-1`; `agentcore status` reports ready (PRD AC2).
- [ ] Invocation payload is validated/unwrapped/defaulted per spec §6.1 (including `min_severity`); an invalid payload terminates `failed`/`INVALID_PARAMS` without cloning (PRD AC28).
- [ ] Credential resolution, token minting, and scrubbing reuse `dependency-update`'s `credentials.py`/`scrubber.py` unmodified against the shared `github_installations` row (PRD AC25, AC26).
- [ ] `config.assert_clock_invariant()` (spec §9.2, this agent's own constants — `MAX_LIFETIME=5400`) runs at entrypoint start and fails fast on drift (PRD AC31 groundwork).
- [ ] A full run against a real repo produces a complete `runs` row with `run_steps` for `resolve_credentials`/`checkout` and a terminal `succeeded`/`no_findings` (no scanners run yet).
- [ ] PostgREST outage does not crash the pipeline; payload appears on stderr/CloudWatch (PRD AC30).

#### Business Rules

- D16 (agent lives at `/agents/security-analyst/`), D17-this-PRD (full-repo posture, not yet exercised), inherited D13/D15/D18/D24(sibling).

#### Technical Notes

- Spec §15.1 (scaffolding), §15.3 (deploy), §7.1-7.3 (PRD requirements 1-14), §9.1-9.3 (reporting/credential integration).
- Copy `agent_reporter.py` byte-identical from `docs/reference/agent_reporter.py`; reuse `pyproject.toml`'s ruff/mypy path-exclusion for it (research finding 8).
- `heartbeat.py`/`signal_backstop.py` copied in this story even though no long step exists yet — cheaper to wire once than to retrofit before S-140.

#### Testing Requirements

- **Unit Tests:** `test_clock_invariant.py` (shipped constants satisfy the chain), payload validate/unwrap/defaults including `min_severity` enum rejection.
- **Integration Tests:** none (no external services beyond what credentials.py already covers, itself reused/untested-here).
- **Manual/UI Testing:** N/A, no UI.
- **Edge-Case Matrix:** missing required field, unknown `mode`, unknown `min_severity`, empty `scanners` list, `prompt`-double-wrapped payload.
- **Acceptance-Criteria Mapping:** PRD AC1→scaffold test; AC2→`agentcore status` manual check; AC25/26/28/30/31→listed unit/component tests above.
- **Execution Commands:** `make test-unit`, `make test-component`, `make validate`.

#### Migration Requirements (When Data Model Changes)

- Not applicable — no schema change (PRD §9).

#### Implementation Steps

1. `agentcore create security-analyst --build Container --entrypoint main.py --code-location app/securityAnalyst/ --protocol HTTP`.
2. Copy `agent_reporter.py`, `credentials.py`, `scrubber.py`, `heartbeat.py`, `signal_backstop.py` from `agents/dependency-update/app/dependencyUpdate/` unmodified.
3. Write `config.py` with this agent's own timeout constants and `assert_clock_invariant()`.
4. Write `main.py`'s payload unwrap/validate/defaults and a placeholder pipeline that goes straight to `succeeded`/`no_findings`.
5. `agentcore deploy -y`; record `runtime_arn` for S-141's seed row.
6. Run against a real (small) target repo; confirm the `runs` row end-to-end.

### Story S-126: Severity normalization (`severity.py`)

**Priority:** High
**Estimated Size:** XS
**Dependencies:** S-125 (project scaffold exists to add a module to).

#### User Story

As an operator, I want every tool's native severity signal normalized into one deterministic 4-level scale, so `min_severity` gating and cross-tool reporting are meaningful instead of comparing apples to oranges.

#### Context

Implements PRD §7.4b (D28-D30) — the severity mapping is pure, tool-isolated, and has no dependency on any scanner actually running yet, so it can land and be fully tested standalone ahead of any scanner integration.

#### Acceptance Criteria

- [ ] Semgrep `ERROR`/`WARNING`/`INFO` map to `high`/`medium`/`low` (PRD AC12a).
- [ ] Every Gitleaks finding maps to `critical`, unconditionally (D29, PRD AC12a).
- [ ] Trivy's four native levels pass through directly; `UNKNOWN` maps to `medium` (D30).
- [ ] Checkov's native severity passes through when present; absence maps to `medium` (D30, the common OSS case).
- [ ] CodeQL uses `security-severity` thresholds (`≥9.0`/`≥7.0`/`≥4.0`) when present, else SARIF `level`, else `medium`.
- [ ] No function inspects free-text rule metadata beyond the named fields (requirement 61).

#### Business Rules

- D28 (fixed deterministic table, no LLM), D29 (Gitleaks always critical), D30 (shared `medium` unknown floor).

#### Technical Notes

- Spec §8.1a — implement exactly the five functions shown there.
- `Severity` enum lives here and is imported by `normalize.py` (S-127) and every scanner normalizer (S-128 through S-132).

#### Testing Requirements

- **Unit Tests:** one parametrized case per table row in PRD §7.4b, per tool — all pure, no fixtures needed beyond raw scalar inputs.
- **Integration Tests:** none.
- **Manual/UI Testing:** N/A.
- **Edge-Case Matrix:** CodeQL with both `security-severity` and `level` present (severity wins); CodeQL with neither; Trivy value outside the known set (defensive `.get()` fallback).
- **Acceptance-Criteria Mapping:** PRD AC12a → `tests/unit/test_severity.py`.
- **Execution Commands:** `make test-unit`.

#### Migration Requirements (When Data Model Changes)

#### Implementation Steps

2. Implement `severity_from_semgrep`/`_gitleaks`/`_trivy`/`_checkov`/`_codeql` exactly per spec §8.1a.
3. Unit test every table row.

### Story S-127: Finding schema, fingerprinting

**Priority:** Critical
**Estimated Size:** S
**Dependencies:** S-126 (`Severity` enum).

#### User Story

As an operator, I want a single normalized `Finding` record and a stable fingerprint derived from it, so every scanner's output can be compared, deduplicated, and diffed on the same terms — including across an unrelated line-shifting edit.

#### Context

Foundation for every scanner normalizer (S-128–S-132), dedup (S-133), classification (S-134), and the re-scan gate (S-137). Getting the fingerprint tolerance band wrong here propagates into every later story, so it lands and is proven first.

#### Acceptance Criteria

- [ ] `Finding`/`Remediation` dataclasses match spec §8.1 exactly.
- [ ] `fingerprint()` is derived from `(file_path, rule_id-or-category, line_range banded)`, not raw tool output (PRD requirement 21/D20).
- [ ] A finding's fingerprint is stable when its line number shifts by less than the tolerance band due to an unrelated edit, and changes when the file or rule changes (PRD AC6).

#### Business Rules

- D20 — fingerprint tolerance band trades a small false-merge risk for a much lower false-new-finding rate.

#### Technical Notes

- Spec §8.1 (schema), §8.2 (fingerprint function, `_LINE_TOLERANCE_BAND = 3`).

#### Testing Requirements

- **Unit Tests:** stability under a small line shift; change on file/rule difference; hash truncation collision-resistance is out of scope (documented assumption, not tested).
- **Integration Tests:** none.
- **Manual/UI Testing:** N/A.
- **Edge-Case Matrix:** line shift exactly at the tolerance boundary; empty `rule_id` falling back to `cwe_or_category`.
- **Acceptance-Criteria Mapping:** PRD AC6 → `tests/unit/test_fingerprint.py`.
- **Execution Commands:** `make test-unit`.

#### Migration Requirements (When Data Model Changes)

- Not applicable.

#### Implementation Steps

1. Define `Finding`/`Remediation` dataclasses.
2. Implement `fingerprint()`.
3. Unit test stability/change behavior directly against the function.

### Story S-129: Gitleaks scanner integration + secret redaction

**Priority:** Critical
**Estimated Size:** M
**Dependencies:** S-127, S-126.

#### User Story

As an operator, I want Gitleaks run against the repository with every finding's matched secret value redacted before it ever reaches a log, artifact, or PR body, so secret detection never itself becomes a secret leak.

#### Context

The redaction obligation (PRD §9.3/§12, R14) is unique to this scanner and load-bearing enough to verify with its own acceptance criterion (PRD AC27) — bundled into this story rather than deferred, since a Gitleaks integration without redaction is not safe to merge even behind a feature flag.

#### Acceptance Criteria

- [ ] Gitleaks runs with `--report-format json`; output normalizes into `Finding` records, severity always `critical` (S-126).
- [ ] `Finding.message` carries only location and rule — **never** the raw matched secret string (PRD AC27).
- [ ] A fixture with a known dummy secret proves the literal secret value is absent from `run_events`, the artifact, and any log output at any verbosity.
- [ ] Runs under its own `SCANNER_TIMEOUT`; crash/timeout is non-fatal to the run (same pattern as S-128).

#### Business Rules

- D29 (always critical), R14 (secret-value redaction — cross-cutting, generalized in S-134/S-139 for other tools' incidental matches).

#### Technical Notes

- Spec §12 — reuses `scrubber.py`'s redaction utility for this different class of sensitive string, not Gitleaks-specific ad hoc logic.
- `remediation = None` always (Gitleaks findings are never mechanical — PRD requirement 23 table).

#### Testing Requirements

- **Unit Tests:** `normalize_gitleaks()` against fixture JSON; redaction function directly, asserting the dummy secret literal is absent from the resulting `Finding.message`.
- **Component Tests:** `run_gitleaks()` subprocess mocked.
- **Manual/UI Testing:** N/A.
- **Edge-Case Matrix:** finding whose matched string appears in multiple places in the raw output (all occurrences redacted, not just the first).
- **Acceptance-Criteria Mapping:** PRD AC27 → `tests/unit/test_gitleaks_redaction.py`.

### Story S-130: Trivy scanner integration (fs/config/image + D24/req 54 boundary)

**Priority:** Critical
**Estimated Size:** L
**Dependencies:** S-127, S-126.

#### User Story

As an operator, I want Trivy's dependency, container, and IaC vulnerability scanning integrated with the exact boundary that keeps npm/pnpm findings out of this agent's fix path, so `security-analyst` and `dependency-update` never compete over the same lockfile while Python dependency fixes stay fully in scope.

#### Context

The single most consequential normalizer in the agent — it is where `lockfile_managed` is decided (PRD D24/requirement 54), which downstream drives the classifier's (S-134) entire mechanical/manual split for this tool.

#### Acceptance Criteria

- [ ] Trivy runs `fs` mode (covering npm/pnpm **and** Python manifests — `requirements.txt`/`poetry.lock`/`Pipfile.lock`), `config` mode, and `image` mode when a Dockerfile is present (PRD requirement 16, 53).
- [ ] `lockfile_managed = True` **only** for `package-lock.json`/`pnpm-lock.yaml` targets; Python manifest targets are `lockfile_managed = False` (PRD requirement 54, spec §8.4's `_JS_LOCKFILES` set).
- [ ] `remediation.kind = "version_bump"` with `target_version` set to the lowest closing version, for both npm/pnpm and Python findings alike (the boundary is applied at classification time, not here).
- [ ] `config`/`image` findings normalize with `remediation.kind = "structural"` or `None` as appropriate — they are never JS/TS-lockfile-boundaried.

#### Business Rules

- D24/requirement 54 — the boundary is decided by target-file inspection here, kept out of the classifier (S-134) per spec §8.4's design note.

#### Technical Notes

- Spec §8.4's `_JS_LOCKFILES` comment block — implement `lockfile_managed` exactly as documented there, including the explicit non-membership of Python manifest filenames.
- PRD requirement 16 — `image` mode targets "the built or a representative base image"; this story's implementation note should record which of the two v1 uses (a representative base image, since building the full image is a separate concern from scanning).

#### Testing Requirements

- **Unit Tests:** `normalize_trivy()` against fixture JSON for each of `fs`(npm)/`fs`(Python)/`config`/`image`; `lockfile_managed` assigned correctly for all four target-file cases (PRD AC11 groundwork — full AC11 verified in S-134).
- **Component Tests:** `run_trivy()` subprocess mocked, three-mode dispatch.
- **Manual/UI Testing:** N/A.
- **Edge-Case Matrix:** repo with no Dockerfile (image mode skipped, requirement 17); repo with both npm and Python manifests present simultaneously.
- **Acceptance-Criteria Mapping:** PRD requirement 53/54 → `tests/unit/test_trivy_runner.py::test_lockfile_managed_boundary`.
- **Execution Commands:** `make test-unit`, `make test-component`.

#### Migration Requirements (When Data Model Changes)

- Not applicable.

#### Implementation Steps

3. Build fixture JSON for all four target-file cases.

### Story S-132: CodeQL scanner integration (JS/TS + Python only)

**Priority:** Critical
**Estimated Size:** L
**Dependencies:** S-127, S-126. **Blocking pre-check:** confirm CodeQL CLI ARM64 availability for the `javascript-typescript` and `python` query packs at the version to be pinned (PRD OQ5, spec §15.2) — do this before starting implementation, not during.

#### User Story

As an operator, I want CodeQL run against JavaScript/TypeScript and Python content only — the two interpreted-language query packs this fleet needs — with a clean skip for any other language, so deep-SAST coverage exists for the operator's primary stack without a compiled-language build surface in the container.

#### Context

The riskiest integration in the agent (research/PRD flag it repeatedly): largest container component, two-phase subprocess call, and the one scanner whose language coverage is a hard product decision (PRD §7.4a) rather than a tool default. Sequenced after the other four scanners so the `ScanResult`/skip/fail pattern is already proven before tackling CodeQL's two-phase call.

#### Acceptance Criteria

- [ ] Container ships exactly two query packs: `javascript-typescript`, `python` — no compiled-language pack (PRD requirement 51).
- [ ] `codeql database create --language=<lang>` triggers no compiled build step for either pack (PRD requirement 14).
- [ ] A repository matching neither pack's trigger condition is `SKIPPED` with a named `run_event`, not a failure (PRD requirement 17, AC24 groundwork).
- [ ] A repository matching both languages runs CodeQL twice, findings merged into one scan pass (spec §8.5).
- [ ] `codeql database analyze --format sarif-latest` output normalizes into `Finding` records via `severity_from_codeql()` (S-126).

#### Business Rules

- D28 (severity via S-126), PRD requirement 51 (exactly two packs, no more).

#### Technical Notes

- Spec §8.5's CodeQL-specific paragraph — the fixed two-entry language table and its trigger conditions (`.js`/`.ts`/`.jsx`/`.tsx`/`package.json` vs. `.py`/`pyproject.toml`/`requirements.txt`).
- Dockerfile change (spec §15.2) is part of this story, not deferred — the scanner cannot be tested without the packs present in the build.

#### Testing Requirements

- **Unit Tests:** `normalize_codeql()` against fixture SARIF (JS/TS and Python separately); language-detection trigger logic for all four combinations (JS only / Python only / both / neither).
- **Component Tests:** `run_codeql()` two-phase subprocess call mocked; skip path verified.
- **Manual/UI Testing:** N/A.
- **Edge-Case Matrix:** SARIF result with neither `security-severity` nor a usable `level` (falls to `medium`, exercising S-126's fallback for real).
- **Acceptance-Criteria Mapping:** PRD requirement 51/AC24 → `tests/component/test_codeql_runner.py`.
- **Execution Commands:** `make test-unit`, `make test-component`.

#### Migration Requirements (When Data Model Changes)

- Not applicable.

#### Implementation Steps

1. **Verify CodeQL CLI ARM64 availability for both packs at the pinned version — do this first, before any code.**
