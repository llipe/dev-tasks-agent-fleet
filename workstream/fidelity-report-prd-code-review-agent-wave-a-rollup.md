## 1. Human-readable summary

Wave A built the whole review agent as code, and it works against recorded GitHub data and a fake model. When it is deployed, someone comments `/review` on a pull request and the agent does the following:

1. It reads the change and its surroundings, the linked issues, the spec, and any verifier report.
2. It asks a model from a different family than the one that wrote the code for a review.
3. It checks the answer against fixed rules. A "must fix" item needs a real location and a concrete way it breaks.
4. It posts one comment with a verdict.

It never approves, merges, or pushes, and it can write only one kind of thing: a comment on the pull request it was asked about.

The agent is **not live yet**. It has no runtime in AWS, its registry entry is switched off, and no `/review` rule exists. Those are Wave B. So the behaviors that need a real GitHub comment or a real model (who may trigger it, the no-loop guard, the seeded-bug smoke) are still to be shown.

All ten stories passed their own audits at "High" with only small, non-blocking differences. Those 102 differences were written back into the requirements documents in one batch, which the user approved. This rollup re-checked that batch against the code. One sentence in the spec lost the actual link-keyword pattern during the rewrite. Another says metrics keys are "always present" more broadly than the code delivers. A few documents still describe the model step as exactly "one call", but the agent can make up to five calls in one review (fallbacks and one repair). None of this changes behavior. Each item is a wording fix for the document owner.
