## 1. Human-readable summary

This story adds the code-review agent's call to the AI model, and everything around it that can go wrong.

The agent asks the model to return its review in a fixed form, so the answer can be checked automatically. Some models refuse parts of the request. When a model refuses the fixed form, the agent asks again in plain text form. When it refuses the "reasoning effort" setting, the agent asks again without it. When the request is too large for the model, the agent asks again without the whole-file copies. Each of these fallbacks happens at most once. If the answer does not have the right form, the agent sends one "please fix this" request with the reason it was rejected. If that also fails, the run fails with a clear error. In the worst case the agent makes five model calls, never more.

Two user decisions are honored throughout. Every call, including the "please fix this" call, stays within the size limit set for the review (D-47). A second "too large" refusal is logged separately so it can be told apart from other errors (D-48).

The quality team found six defects, and all six are fixed. The most important one: each call's waiting time is now sized to the time left in the run, so a slow model can no longer run past the run's deadline. The agent also reports token usage, time spent, cost (when prices are configured), and which answer form was used. Error messages carry only safe identifiers, never the prompt, the model's text, or Amazon's error text.

What should be written down next: the spec still describes the earlier, simpler rules for timing, errors, and the "please fix this" call. One consequence of the size rule deserves a note. When the size limit is small and the review context fills it, the "please fix this" call has room for only a small piece of the model's previous answer (about 1,300 of 56,000 characters at the smallest allowed limit). The model then mostly reviews again with the error in hand. This follows the user's decision and is only recorded here. Three open questions remain: how the size estimate is reported when several calls were made, how the comment will say why whole files were left out, and whether Amazon's real refusal messages match the words the agent looks for. The live checks in S-215 answer the last one.

**Story business rule.** _No tools execute_ (D-07): the adapter never sends `toolResult`, never loops on `stopReason=tool_use`, and a package-wide static scan finds no `toolResult` outside tests (TC-210-17). The repair turn is a user text block rather than an assistant `toolUse` replay precisely so that no tool result is ever needed (pinned 4).

**Judgment 1: do the call sequence and its ≤ 5 cap match D-34, D-35, and R4?** Yes. The forced call comes first (D-34). Each of the three retries (toolChoice fallback, reasoning, context length) runs at most once per run, in whatever order the rejections arrive. The repair call runs at most once and only for invalid output (FR-18). So the bound is 1 + 3 + 1 = 5, which is exactly spec §6.3's list. The worst order (reasoning, toolChoice, context length, invalid, repair) is tested to use exactly 5 calls, and QA's exhaustive walk over every ordering never exceeds the cap or retries a kind twice. D-35's "retries once … records `reasoning_effort_applied=false`" is literal. R4's "retries once with full files removed, logged" is literal, and D-48's distinct warn is present. The rules the spec does not state (retries for review calls only, R4 only when a file is present, reasoning matched first when one message matches several kinds) are bounded and conservative (DR-1). The only open part is whether the substring patterns match the messages Bedrock actually sends (DR-13). A misclassification costs at most one extra call per kind, and it shows up in the warns and in `reasoning_effort_applied`.

**Judgment 2: does D-47 hold for every call, and does the counting cover what the model reads?** Yes, within D-47's own terms. `call()` checks `assert_within_budget(request_tokens(request), B)` before every send: the first call, each retry, and the repair. A violation is `BudgetInvariantError` and nothing is sent. `request_tokens` sums the estimate over every system text, every message text (the repair block included), and `json.dumps(toolConfig)`. Default `ensure_ascii` escapes non-ASCII, which over-counts (QA `test_d47_tool_config_count_is_conservative_for_escaped_text`). `inferenceConfig` and `additionalModelRequestFields` are parameters, not model input. What is not counted cannot be counted: the provider's own chat template and tool-spec rendering (the PR's known limitation), and real token counts for non-Latin text (D-48, accepted). D-47 also says "B + `maxTokens` must fit the model's context window", which S-215 checks at deploy. The spec does not yet carry that sentence (DR-2). The QA probe pins the counted text against what botocore's real serializer sends (`test_d47_counted_text_is_what_botocore_serializes`).

**Judgment 3: is the §8.9 deadline now bounded per step?** Yes, for the adapter's step, provided S-213 wires it as production intends. With `client_factory=make_client` and `deadline`, each call gets a fresh client whose timeouts are `(remaining − 13 s) / 3` per attempt (connect ≤ 10 s, read ≤ 600 s). Under 2 s per attempt (remaining < 19 s), no call starts and the result is `RUN_TIMEOUT`. Each call, with all of botocore's retries and its largest backoff, ends by the deadline, so the sum over the ≤ 5 calls does too. The wire-level QA test shows that a hanging endpoint cannot outlast it. Two conditions remain. First, the bound is per socket read, not per response; a non-streaming reply arrives in one read, so it holds in practice (known limitation, same semantics as the spec's "read timeout"). Second, the bound holds only on the `client_factory` path with a `deadline`: `client=` (tests) checks the deadline before each call only, and no deadline gives 3 × 610 + 13 s. The sizing is stricter than the spec's `min(600 s, time remaining)`: at a full 900 s run, one attempt may read for at most about 266 s (DR-5).

**Judgment 4: is the error mapping consistent with §13?** Yes. Every §13 row the adapter owns maps exactly: `BEDROCK_ACCESS_DENIED`; `BEDROCK_ERROR` for throttling/5xx after botocore's retries and for an unhandled `ValidationException`; `MODEL_OUTPUT_INVALID` after the repair; `RUN_TIMEOUT` when the deadline is reached; `INTERNAL_ERROR` for `CallBudgetExceeded`, `BudgetInvariantError`, `PromptError`, and `SchemaError`. The refinements below go beyond §13's text, and each is in the direction §13 implies (DR-6): timeouts and throttling past the deadline become `RUN_TIMEOUT`, a read timeout before the deadline is `BEDROCK_ERROR`, a reply botocore cannot parse goes to repair, and "no room for a repair" is `MODEL_OUTPUT_INVALID` without a call (unreachable with real builds, per QA's sweep). `BedrockTimeout` subclasses `BedrockError` but sets `code` per instance, so S-213 must map on `.code`, not on the class.

**Judgment 5: are the `output_mode` values the §5.3 ones?** Yes. `OUTPUT_FORCED_SCHEMA = "forced_schema"` and `OUTPUT_PROMPT_JSON = "prompt_json"`, pinned by `test_usage_metrics_use_the_spec_5_3_names`. The mode is that of the last call: `prompt_json` once the fallback fired, including on the error path's partial metrics. `as_metrics()` uses the §5.3 key names and adds `bedrock_calls` (DR-9).

**Judgment 6: QA residual 1, the repair cut at small B.** The auditor reproduced it (seed-free probe, QA's `_full_context_inputs`, a 56,000-char previous output). With every optional block filled, B = 20,000 keeps 1,338 characters in forced mode and 356 in fallback mode, B = 30,000 keeps 2,998 and 2,014, and at B ≥ 60,000 the whole output survives. With a small context, the whole output survives even at B = 20,000. Every repair request was ≤ B. This is what D-47 says: rebuild without full files, then append the previous output "cut to fit the remainder". The rebuild fills B with optional context before the repair block is considered, so at small B there is little remainder. The repair still carries the validator error and the instruction, so at small B it is effectively a second review with the error in hand. The worst outcome is a visible `MODEL_OUTPUT_INVALID`, not a silent overrun. Classified **Minor, Intended**, routed to spec write-back so the consequence is recorded with D-47, plus an S-215 observation of repair success. D-47 is not re-argued here (DR-4).

**Judgment 7: is `FakeConverse` faithful enough for S-213?** Yes, for L2 pipeline tests. It records deep copies of exact requests, answers from a script (responses, exceptions, or callables), and fails on an unexpected call, so a test pins the call count. Its responses pass botocore's Converse output-shape validation. Its errors are the modeled `ClientError` subclasses with full `ResponseMetadata`, and a real `ValidationException` classifies the same as the fixture's (Stubber suite). S-213 must know its limits (see Integration (S-213)): it does not run botocore retries (`throttled()` is the post-retry outcome); its refusal messages are invented until S-215 confirms real ones (DR-13); it has no builders for transport errors; its no-usage response is defensive, not a real shape; and the production path needs `client_factory=lambda **_: fake`.

**Judgment 8: what S-211, S-212, and S-213 must know.** See §5, Integration rows.

**PRD cross-check.** FR-18: forced schema, fallback, one repair, `MODEL_OUTPUT_INVALID`. "One Converse call" is read as one logical review with bounded retries, as spec §6.3 and D-34 already state.
