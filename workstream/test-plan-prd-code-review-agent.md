## 1. Source input summary

- **Mode:** Design (pre-implementation). **Input type:** spec plus stories (whole feature, 12 stories).
- **Scope:** Wave A, base agent (S-204…S-213, #406–#415). Wave B, live (S-214…S-215, #416–#417).
- **System under test:** a Python AgentCore container. A deterministic wrapper loads a PR through an allowlisted
  GitHub REST client and builds a ±50-line expanded diff with `difflib`. It resolves linked issues, the spec,
  and verifier drift candidates, then fits a token budget and makes one Bedrock Converse call (forced `submit_review` schema,
  with fallbacks). It validates the findings, computes the verdict, posts one PR comment, and records an
  `audit_report` artifact. There is no UI, no new table, and no new HTTP endpoint. The trigger is a webhook rule (configuration only).
- **Runners** (per `TESTING.md`):
  - **Agent:** pytest 8.x with directory-based layer markers, as in `security-analyst`. No network in CI.
  - **Panel** (contract side only): Vitest `unit` and `integration` projects. Integration runs against live local
    Supabase (`REQUIRE_LOCAL_DB=1` in CI).
  - **CDK:** jest in `agents/code-review/agentcore/cdk` (not reached by the root aggregate; `TESTING.md` harness defect 6).
- **Risk weighting.** Most of the weight sits on four places:
  - the write surface (the client allowlist, AC-10);
  - the mechanical enforcement of the blocking contract (FR-23, AC-9) and the verdict rule (D-15, D-33);
  - prompt-injection containment (FR-13, AC-13);
  - the context-assembly conventions that come from dev-tasks (issue links, `## Task Checklist`, spec
    mapping, fidelity-report parsing), which can break silently (spec §16 R3).
- **No E2E browser layer.** The panel invoke form is schema-driven and unchanged (PRD §11). The black-box
  end-to-end surface is (a) `invoke` driven at Layer 2 with recorded GitHub fixtures and a fake Bedrock client, and
  (b) the deployed runtime through the real webhook in Wave B.

## 2. Conventions

### 2.1 Paths

| Prefix | Expands to                           |
| ------ | ------------------------------------ |
| `A/`   | `agents/code-review/app/codeReview/` |

Agent tests use the story paths: `A/tests/unit/` (L1), `A/tests/integration/` (L2, see DF-10), and `A/tests/fixtures/`

### 2.2 Layers

| Code | Layer                                                                                                                                                                                  | Command                                                                                    |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| L1   | Unit. Pure functions; `requests` transport stub; fake `converse`. No socket, no database, no wall clock (clock injected).                                                              | `make -C agents/code-review/app/codeReview test-unit`; `pnpm --filter panel run test:unit` |
| L2   | Fixture-driven pipeline: `invoke`/`Pipeline` with recorded GitHub responses, fake Bedrock, reporter sink, prompt sink. The system under test is never replaced at its own entry point. | `make -C agents/code-review/app/codeReview test`                                           |

| Live | Deployed runtime, real GitHub webhook, real Bedrock (Wave B). Evidence goes in the runbook's verification log.                                                                         | `docs/runbooks/code-review-deployment.md` § Verification log                               |
| MR   | Manual or review evidence: a document, change record, configuration screenshot, or PR description check.                                                                               | Reviewer checklist                                                                         |

**Layer-boundary notes.** Provider behavior that is only exercised against the fake Bedrock client (for example,
whether Sol accepts a forced `toolChoice`, or the reasoning field name) is **not** claimed at L2. It is verified Live in
SC-LIVE-08 (`TESTING.md`, Layer 2 must not claim provider behavior that was only tested against a double).
Static source assertions (grep-style tests over the package) are L1.

**Invariants the tests rely on:**

- **I-1** The only GitHub write is `POST /repos/{o}/{r}/issues/{pr_number}/comments` on the invoked PR (FR-27, AC-10).
- **I-2** A run posts at most one review-or-budget comment, plus at most one failure comment (FR-25, FR-26).
- **I-3** Every read after `load_pr` uses the head SHA captured at `load_pr` (FR-3).
- **I-4** Excluded paths, the `## Task Checklist` tail, and earlier PR comments never reach the prompt (FR-10, D-23).
- **I-5** All repository, PR, issue, spec, and report text reaches the model only inside nonce-delimited blocks (FR-13).
- **I-6** The verdict is computed by the wrapper. The model returns no verdict field (§6.3, §8.7).
- **I-7** No posted blocking finding lacks a location in the diff or a failure scenario. No posted finding lacks a consequence (FR-23).
- **I-8** Posted comment text cannot ping users, inject HTML, or re-trigger the rule (§8.8, AC-3).
- **I-9** Secrets (installation token, Supabase key) never appear in the prompt, a comment, an artifact, run_events, or an exception (§12).

### 4.2 S-205 (#407) — GitHub client with a write allowlist

**ACs:**

- **AC1:** client methods `get_pull`, `list_pull_files` (≤ 30 pages), `compare`, `get_content_raw` (404 → `None`), `list_dir`, `get_issue`, `post_pr_comment`.

### 4.3 S-206 (#408) — Expanded diff, file classification, and size check

## 9. Randomized and property tactics (`activity-random-test-tactics`)

iteration. Triage follows the verifier failure-triage workflow: capture, isolate, minimize, classify, report, and at most 3 retries for a
