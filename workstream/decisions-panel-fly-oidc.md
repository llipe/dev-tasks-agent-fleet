| D-01 | Issue | 280/root-cause | Why does the deployed panel get `EACCES` on `/.fly/api`? | — | **Confirmed** on machine `845de5f2e502e8` via `flyctl machine exec` (`flyctl ssh console` returns a WebSocket 502). The socket is `srwxr-xr-x 0:0` (root-owned, mode 0755). Connecting to a unix socket requires write permission, which "other" lacks. A probe `http.request({socketPath:"/.fly/api"})` gets **HTTP 404 as uid 0** (connected) and **`EACCES` as uid 1001** (`nextjs`, from `Dockerfile.panel` `USER nextjs`). Fly creates the socket at Machine boot, so the image build cannot change its mode. | n/a | — | product-engineer | 2026-10-13 |
| D-02 | Issue | 280/regression-window | Did something change that broke a previously working OIDC path? | — | **Yes: the socket's permissions at Machine boot changed. Our image did not.** `USER nextjs` (uid 1001) has been in `Dockerfile.panel` since S-115 (2026-09-08); `panel/lib/aws/` is unchanged since 2026-09-08. The Fly OIDC → STS exchange was confirmed on the deployed Machine on 2026-09-11 (`docs/runbooks/panel-deployment.md` rows 1.13/1.16; tech-guidelines row 1.30), and the 2026-09-16/17 runs show no OIDC failures. The only Machine (re)launch since then is **release v12 (2026-09-20 00:14 UTC)**: the **first deploy through the new CI pipeline** (#248/#249, run `panel-v1.0.1`, `superfly/flyctl-actions/setup-flyctl@master` → flyctl **0.4.104**). Earlier releases, including v11 on 2026-09-17, were deployed locally. `/.fly/api` carries that boot's timestamp (`Sep 20 00:14`) and is `0755 root:root`. There were no runs between 2026-09-17 and 2026-10-13, so the first failure observed is today's. **Not determinable from here:** whether the 0755 mode comes from a Fly platform/init change picked up at relaunch or from the pipeline's newer flyctl. Either way the fix must not depend on the socket's boot-time mode. | n/a | — | product-engineer | 2026-10-13 |
