| D-07 | Issue | 280/token-shape | The entrypoint grant works (socket is `srwxrwxr-x 0:1001`; uid 1001 POST returns HTTP 200), but the deployed panel now fails with `FlyOidcShapeError` instead of `EACCES`. **D-07 evidence (planner, 2026-10-14, production Machine `845de5f2e502e8`, release `panel-v1.1.0` / Fly v13):**
`/.fly/api` is `srwxrwxr-x 0:1001`; as uid 1001, `POST /v1/tokens/oidc {"aud":"sts.amazonaws.com"}` returns **HTTP 200**, `content-type: application/json; charset=utf-8`, body of **1613 bytes that is NOT valid JSON** — it is a **raw JWT** (three base64url segments separated by dots). `deploy-panel.sh`'s probe correctly reported `status=200 token=absent` → exit 3, because the then-current `extractOidcToken`/`tokenIsPresent` accepted **only** a JSON object with a string `value`/`token`. So the EACCES fix (D-03/D-04) succeeded, and this is a distinct, newly-observed shape change: the earlier **2026-09-11** note (PRD panel-v2 §16; tech-guidelines row 1.30) recorded a JSON object; the live Fly platform now returns a bare JWT. **Decision:** `extractOidcToken` first returns the trimmed body verbatim when it matches `^[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]*$`, then falls back to the existing JSON path (string `value`/`token`, or a JSON-encoded JWT string); everything else still throws `FlyOidcShapeError` with **key names only, never any token text**. The audience is still never forwarded to STS (`{aud}` is neither JWT-shaped nor a `value`/`token` string). The probe's `tokenIsPresent` applies the identical rule via a duplicated `isJwtShaped` helper (the probe ships as a single standalone file into the runtime image with no `lib/` beside it, so it cannot import), and a parity-corpus test asserts both files accept/reject the same inputs so they cannot drift.
