## 1. Human-readable summary

This story decides what the code-review agent actually looks at in a pull request. It sorts the changed files into two groups. Files a reviewer should read are shown in full context. Files that are noise or private are only named: lockfiles, generated output, binary files, and the planning notes the PRD says the reviewer must not see. If the readable changes are larger than the agreed limit, the agent stops before downloading anything and reports that the pull request is too big. It never does half a review.

For files within the limit, the agent rebuilds each change itself with 50 lines of surrounding code instead of the 3 lines GitHub provides. It also keeps the full new version of each file and records which lines changed, so a later step can check that every finding points at a changed line. Odd files, such as empty files, files without a final newline, Windows line endings, and invalid text, are handled without crashing. The output always comes out in the same order.

Everything the story asked for is present and tested, and the independent re-run passes. The team made five decisions along the way that the spec does not yet record. The most important one closes a gap that testing found: a file renamed away from a private planning note was showing the note's old content. Now the old content is never fetched, and the file is shown as entirely new. The other four are listed below. The audit found two small new points. First, a file renamed away from a private note is counted at its small reported size, even though the reviewer sees the whole file. A later step still enforces the overall size limit. Second, an empty file or a permissions-only change is labelled "binary". Nothing is lost, because there is nothing in it to review, but the label is wrong.
