## 1. Human-readable summary

This story writes the comment the review agent posts on a pull request. It also writes the two short comments used when a pull request is too big to review and when a run fails.

The review comment shows the verdict first ("blocking" or "clear"), then the problems that must be fixed, then what the verifier found, then the folded-away suggestions, then a line saying what the review looked at, and finally a footer. The footer names what this review does not cover, the model, the rubric version, and a link to the run. Nothing the model or the repository writes can ping a person, link to another issue, add a link or an image, or break the layout. GitHub's own rendering of the sample comment confirms this.

GitHub refuses comments over 65,536 characters. The comment is kept under 60,000 in five steps, as the spec requires. The steps are: drop suggestions, shorten the problem descriptions, shorten the verifier rows, list the remaining problems by title only, and finally cut. The verdict line is never cut. Whenever a step was used, the comment says so and points to the full audit report. The final cut now keeps whole entries and states how many problems it could not show, so a reader always knows how many blocking problems exist.

The developer made 19 wording and layout choices the spec does not spell out, and QA's hostile tests led to six fixes. Most of them only need to be written into the spec and the test plan (DR-1 to DR-3, DR-5 to DR-7, DR-10). Three points need a product decision:

- In an extreme case, the final cut can drop verifier items without saying how many (DR-4).
- The PRD says the rubric version appears on every comment, but the budget and failure comments do not carry it, and neither does the spec's template for them (DR-8).
- The size limit counts characters as Python counts them. If GitHub counts differently, a comment full of emoji could be refused. The run would then post the short failure comment instead (DR-9).

**Story business rule.** _The comment cannot ping users or inject HTML_: delivered. No content `@` lacks U+200B; the only raw `<` are the wrapper's `<details>`, `<summary>`, and `<sub>`; there is exactly one `<!--` and one `-->`. RT-06 asserts this on every iteration, and GitHub's rendering of comment 6369319634 confirms it (the mention is not a link, the `<b>` tag is text). Edge-case matrix: 0 findings (clear snapshot), 40 findings with 1,500-character scenarios (TC-212-13), a title containing `</details>`, and `@everyone` in a scenario (TC-212-09, 10) are all covered.

**Judgment 1: do the layout and the 5-stage size guarantee match §8.8, D-28, and D-36 exactly?** The layout matches the §8.8 template line for line. This covers the marker, the header with the bold verdict and the 7-character SHA, `**B1 · correctness · \`path:120-134\`** — title`, the "Fails when" and "Consequence" items, `**V1 (confirmed)** from \`report\`: row — reason`, "Other drift: 3 items, see the report.", `<details><summary>Suggestions (n)</summary>`, the suggestion shape, `**Context:\*\*`, and the `<sub>` footer text, which is verbatim. The order of the five stages is the spec's, and each one is "apply, then re-measure". The verdict header is never cut: stage 5 keeps the marker and header (`head`) outside the cut region, and probe P3 confirmed this over 300 random hostile bodies. The truncation note is shown whenever any stage ran. Every body after the first measurement is built with the note, stage 5 always adds it, and probe P3 found the note present exactly when `Rendered.stages` is non-empty. The only differences are in presentation, and the developer pinned each one:

- The note sits before the footer rather than after it (pinned 19).
- Stage 4's "N more blocking findings are listed by title only:" leads the list rather than following it, and the one-line entries are bold list items, `- **B7 · correctness · \`path:line\`\*\* — title`, not the spec's plain `B7 · correctness · path:line — title` (pinned 11).
- Stage 5 cuts the middle rather than the tail, so the note and the footer survive, and it cuts blocking entries whole and counts the rest (QA-212-D2).
- Stage 1 shows "Suggestions (k of n)" (pinned 10).

All of these are Intended (DR-1, DR-2). One case is spec-conformant but uneven. Stage 5 counts the blocking findings it cannot show, but not the verifier candidates. In probe P1 (2,000 unchecked candidates, no findings, verdict `blocking`), 46 candidates are rendered, and nothing counts the other 1,954. The "Other drift" line and the context line are cut too. In probe P2 (40 blocking findings at the schema maxima), the Verifier section is dropped entirely. The header and the note stay, so the verdict is never hidden. Reaching this needs about 40 or more escape-heavy candidate rows, which is unlikely. Classified **Minor, Undetermined** (DR-4).

**Judgment 2: do verifier rows come only from wrapper data (D-38), and is the D-33/D-37 status shown honestly?** Yes to both. The row is always `CandidateStatus.candidate.text`, which is S-208's parsed row, neutralized and capped at 1,050, or 300 after stage 3. The model's `reason` is shown only when `reason_from_model` is true. A forged status with a reason but `not_checked` shows "not checked by the model" and never the model's text. A reason that quotes an invented row stays in the reason slot after the em dash. Every candidate is listed, the ones the model saw and the ones dropped for budget (D-37). A `not_reproduced` candidate is listed with the model's reason. Candidates the model omitted and candidates dropped for budget both read `(unchecked) … — not checked by the model`. That is more honest than spec §8.7 and TC-212-06, which label an omitted candidate "confirmed". The reader cannot see which of the two causes applied, but both statements are true, and both count toward `blocking`, which the header shows. Classified with the status vocabulary, **Minor, Intended** (DR-3; it follows S-211 DR-7). The only honesty gap is the stage-5 count in DR-4.

**Judgment 3: is the context line truthful?**

- _S-210 DR-12, "full files omitted to fit the model's context (N files)."_ True in all three cases. `prompt.build_prompt` puts every reviewed, non-removed file that was not included into `full_files_dropped`. The files come from the fill's own drops plus `pieces.left_out`, which is what the R4 context-length retry and the repair rebuild (`include_full_files=False`) leave out. So "no file included, N dropped" means either a context retry left the files out or the budget ran out, and "to fit the model's context" describes both. The renderer reads the `ContextData` of the accepted call, so the line describes the prompt the model actually answered. When some files are included, the line keeps the spec's own "N files too large to include in full: …" with the names. With the DR-12 wording the names are not shown, only the count. That is acceptable.
- _"no text diff" instead of "binary" (S-206 D7)._ True. GitHub returns no patch and no counts for binary files, empty files, and mode-only changes alike, so "binary" could be false and "no text diff" never is. It applies in the context line and in the budget comment's "Not counted" line. The prompt still says `binary` to the model. That is S-209's text and outside this scope.
- _"at least" on a truncated listing._ True. `check_size` (D-11) returns `OverBudget` whenever the listing hit the 3,000-file cap, even when the counted lines are under `max_diff_lines`. In that case `lines` and `files` are lower bounds over the returned files. The message says "at least N lines in at least M files", and it gives the true reason ("Its file list is longer than GitHub returns, so it cannot be reviewed in full within the review budget of X lines") instead of claiming the lines are over the budget. The token path never has `truncated=True`, because a truncated listing ends at `check_size`, before the prompt is built.
- The other clauses are truthful by construction. "issues unavailable (permission)" replaces "no linked issues", never both. A spec left out for budget reads "spec \`x\` omitted (budget)", not "no spec found". The note suffixes come from the fill's `BlockNote`s. The full set of wording choices is recorded as **Minor, Intended** (DR-5).

**Judgment 4: are the budget and failure messages exactly what §8.8 and §13 require?** The failure message is exact: "Code review failed (\`<error_code>\`). [run](…)", on one line, with no exception text. The code is always one of the nine §13 constants, because the caller's object is never rendered (QA-212-D3). The lines budget message is exact: "This PR changes <n> lines in <m> files, over the review budget of <max_diff_lines> lines. Not reviewed." followed by the run link, except that 1 is written "1 line" and "1 file". The link is `PANEL_BASE_URL/runs/<run_id>` with trailing slashes dropped (D-29). The additions all go beyond the §8.8 text, and all are Intended (DR-6):

- the token variant for the §8.4 step 1 overflow, which resolves DF-08, because the line template would state a false count there;
- the "at least" variant;
- the optional "Not counted, listed by name only" line;
- "(run link unavailable)" for an invalid base URL or run ID;
- mapping every non-§13 code to `INTERNAL_ERROR`.

The "issues unavailable (permission)" clause required by §13 is delivered (AC-3). Whether to post at all (no comment for `INVALID_PARAMS`, one comment after `COMMENT_POST_FAILED` unless 401/403) is S-213's decision.
