## 1. Executive Summary

A single-operator web application that presents agent runs along two axes — by agent and by repository — with result, logs, span timeline, and estimated cost, while exposing exactly one write action: enabling or disabling a repository within an agent's scope. It replaces the AWS console as the steady-state surface for monitoring and configuring a fleet of AI agents running on AWS Bedrock AgentCore.

---

## 2. Feature Overview

The control plane reads agent inventory from AWS resource tags, run data from CloudWatch spans, and scope configuration from DynamoDB. It renders four views: an agents list, an individual agent detail (with runs and repos tabs), a repos list, and a run side panel — all built on the same underlying entity (the run) grouped by different filters.

The single write path lets the operator toggle a repository's `enabled` flag or edit its `params` JSON, making scope changes a configuration decision rather than a deploy. The orchestration layer (EventBridge Scheduler + Lambda) fans out to enabled repositories per agent, generating a `session_id` before each fire-and-forget invocation so DynamoDB rows and CloudWatch logs correlate.

---

## 3. Goals & Objectives

1. **Make scope a configuration decision, not a deploy.** Adding or removing a repository from an agent's scope resolves in under 30 seconds, zero deploys.
2. **Establish the repository as a first-class query axis.** Every run is attributable to a subject repository via the `llipe.subject.id` emission contract.
3. **Shorten the path from failure to cause.** Failed run → logs in under 3 clicks.
4. **Remove the AWS console from steady-state operation.** Zero console visits to check on agents.
5. **Keep spend visible enough to notice anomalies.** Token-derived estimate, honestly labeled, under USD 10/month infrastructure.

## 6. User Stories

1. As the operator, I want to see all managed agents in one table so I can assess the fleet's status at a glance.
2. As the operator, I want to view all runs for a specific agent, ordered by date descending, so I can identify recent failures.
3. As the operator, I want to view all agents and runs for a specific repository so I can understand what acted on it.
4. As the operator, I want to open a run's detail (logs, span timeline, metadata) without losing my position in the table.
5. As the operator, I want to toggle a repository's `enabled` state for an agent so scope changes are instantaneous and require no deploy.
6. As the operator, I want to add a new repository to an agent's scope by name so I can onboard repositories without touching code.
7. As the operator, I want to edit a repository's `params` JSON so I can configure agent behavior per-repo.
8. As the operator, I want an estimated 30-day cost per agent so I can spot anomalies without using Cost Explorer.
9. As the operator, I want runs that were cut off at their lifetime limit to be visually distinct from reported failures, so a run that produced no output isn't confused with one that diagnosed a problem.
10. As the operator, I want to filter runs by status and date range so I can focus on what matters.

## 7. Functional Requirements

### 7.1 Single entity: the run

The entire front end is a list of runs. The two grouping views are the same table with a different filter.

| Field | Source |
| --- | --- |
| `session_id` | Generated by the orchestrator |
| `date` | Root span |
| `agent` | Root span |
| `repo` | `llipe.subject.id` attribute |
| `status` | `running` / `success` / `failed` / `incomplete` |
| `duration` | Root span |
| `tokens_in` / `tokens_out` | `gen_ai.usage.*` attributes |
| `estimated_cost` | Calculated |
| `output_url` | `llipe.outcome.url` attribute |

### 7.2 Data sources

| Data | Source | Cache |
| --- | --- | --- |
| Agent inventory | `tag:GetResources`, filter `agent:managed=true` | 5 min |
| Runtime detail + `lifecycleConfiguration` | `bedrock-agentcore-control:GetAgentRuntime` | 5 min |
| Runs | CloudWatch Logs Insights over spans | 5 min |
| Execution logs | `logs:FilterLogEvents` by `session_id` | No cache |
| Configuration | DynamoDB | No cache |

In-process memory cache. No persistence. A container restart clears the cache and loses nothing.

### 7.3 Emission contract

Requirement on the agents. Without this, the per-repository view does not exist.

Attributes on the root span of every run:

```
llipe.subject.id    = "fintrack-home"
llipe.run.status    = "success" | "failed"
llipe.outcome.type  = "pr" | "report" | "none"
llipe.outcome.url   = "https://github.com/myorg/fintrack-home/pull/42"
```

Tokens, latency, and model come from AgentCore's automatic instrumentation. No code required.

**`session_id` is not in the list above, by design.** AgentCore Runtime injects a `session.id` span attribute automatically when the agent runs under ADOT instrumentation, carrying the `runtimeSessionId` passed to `InvokeAgentRuntime`. Since the orchestrator generates that value, the same string appears on the span, in the DynamoDB row, and in the logs, which is what makes the three joinable. Phase 1 must verify the attribute is present before the read path depends on it; if it is absent, the agent sets `llipe.session.id` explicitly as a fallback.

**Application logs in JSON, with `session_id` on every line.** With 3–5 repos running in parallel, filtering by time window mixes runs together.

### 7.4 Discovery tags

```
agent:managed = "true"     # the only filter the front end uses
agent:name    = "dep-updater"
agent:domain  = "security"
```

An agent without `agent:managed=true` does not appear in the front end. This is the opt-in mechanism.

### 7.5 Views

#### A. Agents

Table. One row per agent discovered by tag.

Columns: name, domain, last run (relative), last run status, active repos, estimated 30d cost.

Click a row → Agent view.

#### B. Agent

Two tabs.

**Runs** — table filtered by agent.
Columns: date, repo, status, duration, tokens, estimated cost, output.
Order: date descending. Filter by status and date range.
Click a row → Run panel.

**Repos** — the configuration table.
Columns: repo, `enabled` (toggle), last run, last status, output.
Actions: toggle `enabled`, add repo (name input), edit `params` (JSON in a textarea, validated before saving).

#### C. Repos

Table. One row per `SUBJECT#`.

Columns: repo, agents covering it, last activity, status.

Click → Repo view: the same runs table as B, filtered by repo instead of agent. Includes an agent column.

#### D. Run (side panel)

Opens from any table without losing context.

- Metadata: agent, repo, `session_id`, status, duration, tokens, estimated cost, link to output.
- Span timeline: model and tool calls, with latency and tokens per call.
- Logs: `FilterLogEvents` filtered by `session_id`.

### 7.6 Estimated cost

```
cost = (tokens_in × price_in + tokens_out × price_out)
```

Pricing table as a versioned JSON file in the front end's repo, indexed by `model_id`. Displayed labeled as an estimate.

Does not include runtime compute cost. That only comes from Cost Explorer, which is out of scope.

## 8. Business Rules

### 8.1 DynamoDB schema

Single table, inverted GSI.

```
PK                      SK                  attributes
SUBJECT#fintrack-home   META                enabled
SUBJECT#fintrack-home   AGENT#dep-updater   enabled, params{},
                                            last_session_id, last_run_at,
                                            last_status, last_outcome_url
AGENT#dep-updater       CONFIG              global params

GSI1: PK = SK, SK = PK
```

**Access patterns:**

- Repos for an agent: `Query GSI1 PK = AGENT#dep-updater`, filter `enabled = true`
- Agents for a repo: `Query PK = SUBJECT#fintrack-home`
- Add a repo to scope: a single `PutItem`

### 8.2 Write separation

| Writer | Attributes |
| --- | --- |
| Front end | `enabled`, `params` |
| Orchestrator | `last_session_id`, `last_run_at`, `last_status = running` |
| Agent | `last_status`, `last_outcome_url` |

The agent uses `UpdateExpression` on those two attributes only. Never `PutItem`. Constrain with `dynamodb:Attributes` on the execution role's policy.

### 8.3 Orchestration

One schedule per agent. The Lambda does the fan-out.

```
EventBridge Scheduler (cron)
  → Orchestrator Lambda
      → Query GSI1: AGENT#dep-updater, enabled=true → [N repos]
      → per repo:
          session_id = "dep-updater-fintrack-home-20260824-060000"
          UpdateItem: last_session_id, last_run_at, last_status="running"
          InvokeAgentRuntime(session_id, payload)   ← does not wait for a response
      → returns
```

**Session ID generated by the orchestrator.** Fire-and-forget doesn't return an ID from AWS. Generating it before invocation is what lets the DynamoDB row correlate with the logs. Minimum 33 characters, required by `InvokeAgentRuntime`.

**Payload:**

```json
{
  "session_id": "dep-updater-fintrack-home-20260824-060000",
  "repo": "myorg/fintrack-home",
  "params": { "allow_fixes": true, "max_fix_attempts": 3 }
}
```

**Concurrency:** a pool of 3–5 parallel invocations. Serial execution stacks up latency; all at once hits GitHub and Bedrock rate limits.

### 8.5 Agent liveness

Fire-and-forget only works if the agent stays alive after the caller disconnects, and that is not automatic.

AgentCore polls the agent's `/ping` endpoint to decide whether a session is still active. It must return `{"status": "HealthyBusy"}` while work is in progress; a session reporting idle is terminated after `idleRuntimeSessionTimeout`. Because `/ping` is served by the same process as the entrypoint, **an entrypoint that runs its pipeline synchronously blocks the health check**, and the platform terminates the session mid-work with no error emitted.

Every agent therefore returns from its entrypoint immediately and runs the real work on a background thread tracked with the AgentCore SDK's async-task helpers. Terminal writes — the DynamoDB outcome stamp and the `llipe.*` span attributes — happen in a `finally` block so a crash still closes the run out.

This is also what makes the orchestrator's fire-and-forget invocation safe: there is no long-lived response to abandon.

**Partial failures:** if one repo fails, the rest continue. Each repo is an independent run.

**`incomplete` status:** derived by the front end at read time. `last_status = running` and elapsed time past the agent's own configured `maxLifetime` (plus a 5-minute grace). Nobody writes it. This is what catches an agent that died without closing out.

`maxLifetime` comes from `GetAgentRuntime`'s `lifecycleConfiguration`, per agent, so the threshold is the platform's own limit rather than a guess. Past that point AgentCore has terminated the instance, so "no outcome was written" is a fact, not an inference — the run produced no output. That is why the status is `incomplete` and not `failed`: nothing reported a failure, the run was cut off. A late write from a recovering agent still moves it to `success` or `failed`.

If `maxLifetime` is absent from the response, fall back to the AgentCore service default of 28800 s (8 h).

> Superseded: v1.0 and v1.1 specified a fixed 6-hour `stale` threshold. That is wrong in both directions. The reference agent configures `maxLifetime: 3600` (1 hour), so a dead run would have shown as `running` for five hours longer than the runtime could possibly have been alive; and against the 8-hour service default, a legitimately long run would have been flagged dead two hours early.

### 8.4 GitHub

A GitHub App installed on the org. Private key in Secrets Manager. The agent requests an installation token scoped to the repo in the payload.

Permissions: `contents:write`, `pull_requests:write`.

The repo list is the DynamoDB allowlist. The agent does not discover repos through the GitHub API. A new repo enters scope only by explicit decision in the front end.

## 11. Design Considerations

### 11.1 UI/UX

Refer to [`/DESIGN.md`](../DESIGN.md) for the full design contract. Key points:

- The run is the only entity. All views are a table of runs with different groupings.
- Dense, scannable tables. The table is the product.
- The run panel opens as a right-side sheet, preserving table context.
- Status is never communicated by colour alone — always paired with a text label.
- Loading, empty, error, and timed-out states are designed, not absent.
- Filter state serialized to URL query parameters for sharability and reload resilience.

## 12. Technical Considerations

### 12.1 Authentication

Cloudflare Access in front of the app.

**The app validates the `Cf-Access-Jwt-Assertion` JWT against the team's JWKS.** Without that validation, anyone can hit the `.fly.dev` origin directly and Cloudflare Access accomplishes nothing.

Lock down the origin with a Cloudflare Tunnel or a Cloudflare IP allowlist.

### 12.2 IAM

One role. Credentials via Fly Machines OIDC assuming a role via web identity. If OIDC adds friction, static access keys in Fly secrets with the same minimal permissions.

**Read:**

```
tag:GetResources
bedrock-agentcore-control:GetAgentRuntime
bedrock-agentcore-control:ListAgentRuntimes
logs:StartQuery
logs:GetQueryResults
logs:FilterLogEvents
```

**Write:**

```
dynamodb:GetItem, Query, PutItem, UpdateItem, DeleteItem
```

on the table and GSI1.

No `bedrock-agentcore:InvokeAgentRuntime`. No write action on runtimes at all. The policy is the enforcement of the scope defined in Section 10.

### 12.3 Repository layout

Independent public repo, monorepo. Does not depend on `dev-tasks` and does not live inside it.

**Name:** `dev-tasks-agent-fleet`.

```
dev-tasks-agent-fleet/
├── apps/
│   └── control-plane/          # Next.js, deploys to Fly.io
├── agents/
│   ├── dep-updater/             # deploys to AgentCore
│   └── ...
├── packages/
│   └── shared/                  # shared types: DynamoDB schema, emission contract
└── infra/
    ├── control-plane.fly.toml
    └── agents/                  # per-agent infra + orchestrator Lambda
```

**Why a monorepo:** the front end and the agents share two contracts — the DynamoDB schema and the `llipe.*` span attributes — that today exist only as convention in this document. `packages/shared` turns them into a type both sides import, instead of two implementations that can drift apart unnoticed.

**Why not a single deploy:** the front end deploys to Fly, the agents deploy to AgentCore. Different cycles. CI gated by path (`apps/control-plane/**` triggers the front-end deploy, `agents/**` triggers the matching agent's deploy) so a change to one agent doesn't redeploy the front end and vice versa.

### 12.4 Prerequisites

1. **CloudWatch Transaction Search enabled.** Without this there are no spans and no tokens. 1% indexing is sufficient: 100% of spans are ingested as logs; the indexing percentage only affects X-Ray trace summaries.
2. **A unified span destination** across the fleet. Per-runtime log group or shared `aws/spans`, pick one. Two destinations means two queries.
3. **Tags applied** to existing agents.
4. **Emission contract implemented** in the dependency-update agent.

## 15. Assumptions

1. 1% Transaction Search indexing is sufficient — all spans ingested as logs; indexing only affects X-Ray trace summaries.
2. A single span destination is achievable across the fleet.
3. A 5-minute cache TTL is acceptable freshness for inventory, runtime detail, and run lists.
4. `maxLifetime` from `GetAgentRuntime` is the correct bound for deriving `incomplete`, and a 5-minute grace covers instance termination plus span and DynamoDB write lag.
5. Token-derived cost is close enough to be useful for anomaly detection.
6. A hand-maintained pricing table stays current enough.
7. AgentCore's automatic instrumentation supplies tokens, latency, and model without agent-side code.
8. Cloudflare Access plus origin lockdown is adequate authentication for a single-user tool.

## 17. Security & Compliance

- **IAM least privilege:** No `InvokeAgentRuntime`, no write on runtimes. The policy enforces §10.
- **Write separation enforced by policy:** Agent role constrained with `dynamodb:Attributes` to prevent `PutItem` (which would overwrite `enabled`/`params`).
- **JWT validation:** `Cf-Access-Jwt-Assertion` verified against team JWKS. Fail closed — if JWKS fetch fails, deny.
- **Origin lockdown:** Cloudflare Tunnel or IP allowlist. Not optional — without it, JWT validation is the only control.
- **`params` is an injection boundary:** Validated with a key allowlist on write, re-validated in the agent on read. Never passed to shell, template, or prompt without appropriate escaping.
- **GitHub App:** Private key in Secrets Manager. Installation tokens per-repo, short-lived, never logged.
- **No PII beyond repository names.** No data-retention policy required.
- **Transport:** HTTPS only, HSTS enabled.
- **Dependencies:** Exact version pins, committed lockfiles, vulnerability scanning in CI.

## Implementation Order

1. Create the `dev-tasks-agent-fleet` repo with the layout from §12.3 and path-gated CI workflows.
2. Enable Transaction Search and unify the span destination.
3. Apply tags to existing agents.
4. Rebuild `dep-updater` in the monorepo under `agents/` and implement the emission contract, using `packages/shared` for the `llipe.*` attributes.
5. Create the DynamoDB table and load the current repo list.

7. Build the front end in `apps/control-plane`.

Order matters: steps 2–5 generate the data the front end consumes. Building the front end first leaves empty tables.
