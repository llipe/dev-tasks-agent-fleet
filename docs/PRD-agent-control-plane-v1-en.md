# PRD — Agent Control Plane

**Author:** Llipe
**Date:** 2026-08-18
**Version:** 1.0
**Status:** Scope closed

---

## 1. Problem

Agents run on AWS Bedrock AgentCore. Operating them requires the AWS console, which is organized by service: runtimes on one side, logs in CloudWatch, configuration nowhere.

Two concrete consequences:

1. **Changing an agent's scope requires a deploy.** Adding a repository to the dependency-update agent's list is a code change.
2. **There is no per-repository view.** AWS has no such concept. "What did all agents do to `fintrack-home` this month" is not a possible query.

## 2. Objective

A web app for personal use that shows agent runs along two axes — agent and repository — with result, logs, and estimated cost. It allows one write action: enabling or disabling a repository within an agent's scope.

## 3. Out of scope

Explicit list. None of this ships in v1:

- Creating, deploying, modifying, or deleting agent runtimes.
- Invoking agents on-demand from the front end.
- Cost Explorer, cost allocation tags, actual billed cost.
- Local database, materialization job, custom run ledger.
- Configuration Bundles and prompt versioning.
- Schema-driven forms.
- Quality evaluation, prompt optimization, tool-usage analysis.
- Missing-run detection based on declared schedule.
- Aggregate health metrics, outcome distributions, trends.
- Alerts via Slack, email, or any external channel.
- Differentiated roles and permissions.
- Multi-account and multi-region.

## 4. Single entity: the run

The entire front end is a list of runs. The two grouping views are the same table with a different filter.

| Field | Source |
|---|---|
| `session_id` | Generated by the orchestrator |
| `date` | Root span |
| `agent` | Root span |
| `repo` | `llipe.subject.id` attribute |
| `status` | `running` / `success` / `failed` / `stale` |
| `duration` | Root span |
| `tokens_in` / `tokens_out` | `gen_ai.usage.*` attributes |
| `estimated_cost` | Calculated |
| `output_url` | `llipe.outcome.url` attribute |

## 5. Data sources

| Data | Source | Cache |
|---|---|---|
| Agent inventory | `tag:GetResources`, filter `agent:managed=true` | 5 min |
| Runtime detail | `bedrock-agentcore-control:GetAgentRuntime` | 5 min |
| Runs | CloudWatch Logs Insights over spans | 5 min |
| Execution logs | `logs:FilterLogEvents` by `session_id` | No cache |
| Configuration | DynamoDB | No cache |

In-process memory cache. No persistence. A container restart clears the cache and loses nothing.

## 6. Emission contract

Requirement on the agents. Without this, the per-repository view does not exist.

Attributes on the root span of every run:

```
llipe.subject.id    = "fintrack-home"
llipe.run.status    = "success" | "failed"
llipe.outcome.type  = "pr" | "report" | "none"
llipe.outcome.url   = "https://github.com/myorg/fintrack-home/pull/42"
```

Tokens, latency, and model come from AgentCore's automatic instrumentation. No code required.

**Application logs in JSON, with `session_id` on every line.** With 3-5 repos running in parallel, filtering by time window mixes runs together.

## 7. Discovery tags

```
agent:managed = "true"     # the only filter the front end uses
agent:name    = "dep-updater"
agent:domain  = "security"
```

An agent without `agent:managed=true` does not appear in the front end. This is the opt-in mechanism.

## 8. DynamoDB

Single table, inverted GSI.

```
PK                      SK                  attributes
SUBJECT#fintrack-home   META                enabled
SUBJECT#fintrack-home   AGENT#dep-updater   enabled, params{},
                                            last_session_id, last_run_at,
                                            last_status, last_outcome_url
AGENT#dep-updater       CONFIG              global params

GSI1: PK = SK, SK = PK
```

**Access patterns:**

- Repos for an agent: `Query GSI1 PK = AGENT#dep-updater`, filter `enabled = true`
- Agents for a repo: `Query PK = SUBJECT#fintrack-home`
- Add a repo to scope: a single `PutItem`

**Write separation:**

| Writer | Attributes |
|---|---|
| Front end | `enabled`, `params` |
| Orchestrator | `last_session_id`, `last_run_at`, `last_status = running` |
| Agent | `last_status`, `last_outcome_url` |

The agent uses `UpdateExpression` on those two attributes only. Never `PutItem`. Constrain with `dynamodb:Attributes` on the execution role's policy.

## 9. Orchestration

One schedule per agent. The Lambda does the fan-out.

```
EventBridge Scheduler (cron)
  → Orchestrator Lambda
      → Query GSI1: AGENT#dep-updater, enabled=true → [N repos]
      → per repo:
          session_id = "dep-updater-fintrack-home-20260824-060000"
          UpdateItem: last_session_id, last_run_at, last_status="running"
          InvokeAgentRuntime(session_id, payload)   ← does not wait for a response
      → returns
```

**Session ID generated by the orchestrator.** Fire-and-forget doesn't return an ID from AWS. Generating it before invocation is what lets the DynamoDB row correlate with the logs. Minimum 33 characters, required by `InvokeAgentRuntime`.

**Payload:**

```json
{
  "session_id": "dep-updater-fintrack-home-20260824-060000",
  "repo": "myorg/fintrack-home",
  "params": { "branch": "main", "severity": "high", "ignore": ["lodash"] }
}
```

**Concurrency:** a pool of 3-5 parallel invocations. Serial execution stacks up latency; all at once hits GitHub and Bedrock rate limits.

**Partial failures:** if one repo fails, the rest continue. Each repo is an independent run.

**`stale` status:** derived by the front end at read time. `last_status = running` with `last_run_at` older than 6 hours. Nobody writes it. This is what catches an agent that died without closing out.

## 10. GitHub

A GitHub App installed on the org. Private key in Secrets Manager. The agent requests an installation token scoped to the repo in the payload.

Permissions: `contents:write`, `pull_requests:write`.

The repo list is the DynamoDB allowlist. The agent does not discover repos through the GitHub API. A new repo enters scope only by explicit decision in the front end.

## 11. Views

### A. Agents

Table. One row per agent discovered by tag.

Columns: name, domain, last run (relative), last run status, active repos, estimated 30d cost.

Click a row → Agent view.

### B. Agent

Two tabs.

**Runs** — table filtered by agent.
Columns: date, repo, status, duration, tokens, estimated cost, output.
Order: date descending. Filter by status and date range.
Click a row → Run panel.

**Repos** — the configuration table.
Columns: repo, `enabled` (toggle), last run, last status, output.
Actions: toggle `enabled`, add repo (name input), edit `params` (JSON in a textarea, validated before saving).

### C. Repos

Table. One row per `SUBJECT#`.

Columns: repo, agents covering it, last activity, status.

Click → Repo view: the same runs table as B, filtered by repo instead of agent. Includes an agent column.

### D. Run (side panel)

Opens from any table without losing context.

- Metadata: agent, repo, `session_id`, status, duration, tokens, estimated cost, link to output.
- Span timeline: model and tool calls, with latency and tokens per call.
- Logs: `FilterLogEvents` filtered by `session_id`.

## 12. Estimated cost

```
cost = (tokens_in × price_in + tokens_out × price_out)
```

Pricing table as a versioned JSON file in the front end's repo, indexed by `model_id`. Displayed labeled as an estimate.

Does not include runtime compute cost. That only comes from Cost Explorer, which is out of scope.

## 13. Stack

| Layer | Choice |
|---|---|
| Framework | Next.js App Router, `output: 'standalone'` |
| Components | shadcn/ui + Tailwind |
| Tables | TanStack Table |
| Deployment | Fly.io, single container |
| State | No database. In-memory cache |

AWS calls happen server-side. Server components mean no API layer to write or maintain.

## 14. Authentication

Cloudflare Access in front of the app.

**The app validates the `Cf-Access-Jwt-Assertion` JWT against the team's JWKS.** Without that validation, anyone can hit the `.fly.dev` origin directly and Cloudflare Access accomplishes nothing.

Lock down the origin with a Cloudflare Tunnel or a Cloudflare IP allowlist.

## 15. IAM

One role. Credentials via Fly Machines OIDC assuming a role via web identity. If OIDC adds friction, static access keys in Fly secrets with the same minimal permissions.

**Read:**
```
tag:GetResources
bedrock-agentcore-control:GetAgentRuntime
bedrock-agentcore-control:ListAgentRuntimes
logs:StartQuery
logs:GetQueryResults
logs:FilterLogEvents
```

**Write:**
```
dynamodb:GetItem, Query, PutItem, UpdateItem, DeleteItem
```
on the table and GSI1.

No `bedrock-agentcore:InvokeAgentRuntime`. No write action on runtimes at all. The policy is the enforcement of the scope defined in Section 3.

## 16. Repository

Independent public repo, monorepo. Does not depend on `dev-tasks` and does not live inside it.

**Name:** `dev-tasks-agent-fleet`.

**Layout:**

```
dev-tasks-agent-fleet/
├── apps/
│   └── control-plane/          # Next.js, deploys to Fly.io
├── agents/
│   ├── dep-updater/             # deploys to AgentCore
│   └── ...
├── packages/
│   └── shared/                  # shared types: DynamoDB schema, emission contract
└── infra/
    ├── control-plane.fly.toml
    └── agents/                  # per-agent infra + orchestrator Lambda
```

**Why a monorepo:** the front end and the agents share two contracts — the DynamoDB schema and the `llipe.*` span attributes — that today exist only as convention in this document. `packages/shared` turns them into a type both sides import, instead of two implementations that can drift apart unnoticed.

**Why not a single deploy:** the front end deploys to Fly, the agents deploy to AgentCore. Different cycles. CI gated by path (`apps/control-plane/**` triggers the front-end deploy, `agents/**` triggers the matching agent's deploy) so a change to one agent doesn't redeploy the front end and vice versa.

## 17. Prerequisites

1. **CloudWatch Transaction Search enabled.** Without this there are no spans and no tokens. 1% indexing is sufficient: 100% of spans are ingested as logs; the indexing percentage only affects X-Ray trace summaries.
2. **A unified span destination** across the fleet. Per-runtime log group or shared `aws/spans`, pick one. Two destinations means two queries.
3. **Tags applied** to existing agents.
4. **Emission contract implemented** in the dependency-update agent.

## 18. Success metrics

- Adding a repo to an agent's scope: under 30 seconds, zero deploys.
- From the run list to the log of a failed run: under 3 clicks.
- AWS console opens to check on agents: zero in steady state.
- Monthly infrastructure cost of the control plane: under USD 10.
